# Design decisions

Rulings on points the specification (`docs/spec.md`) leaves open or where the project departs from its wording. A requirement that rests on one of these cites it in `Source`. A requirement with no true parent of its own uses `Derived(DD-nnn)` in `Parent(s)`.

"User" in the Source column means the project owner decided it during planning. "Engineering" means it was set during planning to close a gap and can be challenged at review.

| ID | Title | Decision | Rationale | Source |
| --- | --- | --- | --- | --- |
| DD-001 | Essential loads | A load may carry optional `essential: true` (default false). A configuration fails if any essential load is unpowered, meaning its bus is de-energised or its crew switch is off. Each one is reported. | Capacity checks alone report PASS when every source has failed, because nothing is overloaded. This closes spec §9 item 3. | User |
| DD-002 | Bus demand is throughput | Bus demand, bus label values and the bus capacity check use throughput: the bus's own loads plus everything fed through it, including TRU input power after efficiency. Own-load power is reported separately. | Departs from §3.4 step 1. A busbar's rating applies to what it carries, and §3.4 alone would hide overloads on feeding buses. | User |
| DD-003 | UI verification | Front-end requirements are verified with Playwright browser tests driven from pytest. Playwright is a dev-only dependency. The shipped front end stays vanilla JS with no build step. | Every UI requirement gets a repeatable test. | User |
| DD-004 | Flow inside an island | Flow on each closed contactor is found from node balance on a spanning tree of the island: the tree is rooted at the source with the lowest id, and the power crossing a contactor is the net demand on the side away from that root. If the island has a closed loop, a deterministic spanning tree is used (breadth-first from the source with the lowest id, neighbours in id order), the contactors left out carry zero, and a `meshed_island` warning names them. | Spec §3.4 assumes a unique upstream path. A loop makes the split indeterminate without impedances, which are out of scope. The warning keeps the assumption visible. | Engineering |
| DD-005 | Paralleled AC island | An AC island with more than one live source, operative or available, is a configuration error. Its buses remain energised and its loads count. Bus demand on that island is own loads plus TRU input power only, and no demand is attributed to its sources or contactors, so those elements are not capacity-checked. Downstream DC islands are analysed as normal. | §3.5 requires the failure message but not the numbers. Splitting power between unsynchronised sources would be invented data. | Engineering |
| DD-006 | DC source sharing | All non-battery DC sources feeding an island (TRUs and DC RAT outputs) share demand in proportion to continuous capacity, for all three bands. Two or more batteries that are the sole sources on an island share the same way. If the total continuous capacity is zero, the split is equal. | §3.5 covers only TRU with TRU. This generalises the same rule without adding a new concept. | Engineering |
| DD-007 | TRUs hang off buses | `input_bus` and `output_bus` are required. A RAT output feeding a TRU "directly" (§4.3) is modelled through a small dedicated AC bus. A TRU needs exactly one input contactor from `input_bus` and exactly one output contactor to `output_bus`. Anything else is a validation error. | Keeps the schema in §5.1 unchanged and gives one energisation rule. | Engineering |
| DD-008 | RAT outputs are separate sources | Each RAT output is its own source entry with its own state and capacity, as in §5.1. They are clicked independently and there is no combined limit across outputs. | Follows the sample schema. | Engineering |
| DD-009 | Scenario state validation | A `states` key that matches no stateful component, or a value invalid for that component, is a validation error. Valid values: engine, APU, battery and TRU take `operative` or `failed`; emergency generator takes `available` or `unavailable`; contactor takes `closed` or `open`; a crew-switched bus takes `on` or `off`. The interactive analyse endpoint applies the same check. | §5.2 calls dangling references errors. This makes the rule precise. | Engineering |
| DD-010 | Band handling | The three band keys are fixed: `transient`, `short_term`, `continuous`. Labels come from `settings.bands`, which is optional and has defaults. A `power` or `capacity` object missing a band is an error, and negative values are errors. Band ordering is not enforced (§3.1). | §3.1 says every load and capacity is defined in three bands. | Engineering |
| DD-011 | Remaining margin | Remaining margin (W) = capacity − demand × (1 + margin). Remaining margin (%) = that value ÷ capacity × 100, negative when overloaded. The worst element of a configuration is the checked element and band with the smallest percentage. If nothing is checked, worst element and margin are null. Zero capacity with non-zero demand is treated as −100 %, and zero capacity with zero demand as 0 %. De-energised elements are not checked. | The spec uses the term in §6.2 and §6.3 without defining it. A percentage compares elements of different sizes fairly. | Engineering |
| DD-012 | Failed sources do not bridge | A source with several contactors connects those buses only while it is operative or available. A failed or unavailable source is not a path, and neither is a failed TRU. | §3.3: "A failed source supplies nothing." | Engineering |
| DD-013 | Contactor demand and energisation | A contactor's demand is the power crossing it, found by node balance: for a source with one contactor this is the source output, and a source with several contactors splits it. A TRU input carries input power and a TRU output carries output power, and ties carry cut-set flow. DD-005 takes precedence on a paralleled island, where no demand is attributed to contactors. A contactor is energised when it is closed and at least one end is energised. | Needed to check rated contactors (§3.6) and to colour them (§6.2). | Engineering |
| DD-014 | TRU output open | A TRU with input power and an open output contactor is energised but feeds nothing and has zero demand. | §3.3 defines TRU energisation by the input side only. | Engineering |
| DD-015 | Battery priority wording | "Any other energised DC source" in §3.5 means a TRU or DC RAT output feeding that island now: operative or available, energised, with its contactor closed. Battery charging is not modelled. | A failed TRU or one with an open output contactor must not silence the battery. | Engineering |
| DD-016 | Upload and export behaviour | The definition id is the file stem. Uploads are validated first, invalid ones are rejected with HTTP 422 and not stored, valid ones are saved in `definitions/` under a sanitised name, and a name already in use returns HTTP 409. Last batch results are held in memory per definition, and export before any run returns HTTP 404. The server binds to localhost, with no authentication. | §6.1 and §7.2 are indicative. This is a local single-user tool. | Engineering |
| DD-017 | Validator warnings | Unknown keys, a contactor joining nodes of the same kind but different nominal voltage, a source with no contactor, and a bus with no possible feed are warnings, not errors. They are shown but do not block loading. | §5.2 lists the errors. These are suspicious but legal. | Engineering |
| DD-018 | Runtime and CLI | Python 3.12 or later, managed with uv. CLI exit codes: 0 all scenarios pass, 1 at least one fails, 2 invalid definition or bad usage. `ela batch` also accepts `--csv PATH` and `--json PATH`. | §6.3 needs non-zero on failure. Separating invalid input from failed analysis makes it usable in automation. | Engineering |
| DD-019 | Battery-only has no AC | The component model has no inverter, and §5.2 forbids DC to AC conversion. On battery only, every AC bus is dead. The sample marks as essential only loads that its battery-only configuration can reach. | A static inverter is outside the spec's component list. | Engineering |
| DD-020 | Default configuration | The sample's default state must be a valid, passing configuration, with the APU line contactor and RAT contactors chosen so defaults cause no AC paralleling. Scenarios list contactors explicitly where reconfiguration is needed, since there is no automatic transfer (§2). | §5.1's S03 sets only source states, which is enough only if defaults already isolate the buses. | Engineering |
| DD-021 | RAT default state | `default_state` on an emergency generator is honoured when present, and it defaults to `unavailable` when absent. | §4.3 and §5.1 differ. Honouring an explicit value keeps one rule for all components. | Engineering |
| DD-022 | Batch row and touch gestures | A batch row has a separate expand control, and clicking the rest of the row opens the scenario. On touch, tapping a clickable schematic element both toggles it and shows its tooltip. | §6.3 gives both actions to the row, and on touch §6.2's tap and click are the same gesture. | Engineering |
| DD-023 | Numeric tolerance | The capacity comparison treats demand × (1 + margin) ≤ capacity as true when the excess is within 1e-6 W. Margins within 1e-6 % are equal when ranking worst elements. | IEEE arithmetic makes 3000 × 1.1 exceed 3300, which would fail an exact-limit case that §3.6 says passes. | Engineering |
| DD-024 | Published interface names | The Python entry points, JSON result fields, HTTP bodies and DOM hooks listed under "Names used by the cases" in `docs/test-cases.md` are binding interface requirements. The server reads its definitions folder from `ELA_DEFINITIONS_DIR`, defaulting to `definitions/` at the repository root. | Without fixed names the tests cannot be written before the code, and upload tests would write into the real folder. | Engineering |
| DD-025 | No essential loads warning | The validator warns when a definition marks no load as essential. | With no essential loads, total power loss still reports PASS under DD-001. The warning keeps that visible without changing the pass rule. | Engineering |
